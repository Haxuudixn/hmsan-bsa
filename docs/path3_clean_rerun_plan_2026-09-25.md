### 2.1 F9 结论：A4 的 `mat2 on cpu:0` 不是代码 bug（2026-09-25 复查）

原判断"未门控融合分支自己造了 CPU 张量"被三条证据推翻：

1. **所有模块都在 `__init__` 里建、且都是注册子模块。** 递归扫描 `src/` 后，每个
   `nn.Linear/LayerNorm/Embedding/Parameter` 都落在 `__init__` 内（`page_encoder.py`
   的 251–254、291–292、344–345、389–392 等看似可疑的行，实际都在各自的 `__init__` 里），
   没有任何惰性建模块；`nn.ModuleList/ModuleDict` 之外没有用裸 list/dict 存模块。
   因此 `.to(device)` 必然覆盖全部权重。
2. **所有非参数张量都显式带 `device=`**；全树唯一的 `.cpu()` 都在指标/落盘路径，
   不进任何 matmul。
3. **崩溃当场没有显存压力**：`monitor.csv` 显示 21:27:41 前后占用仅
   **5.9 GB / 12.3 GB**、温度 61 ℃、功耗 87 W。所以不是"OOM 触发 CPU 回退"。

另外，同一个 preset、同一 seed、同一数据顺序的**下一次重试在同一步没有复现**，
并继续跑到 76/303 才被人工停止（`exit=-1`）。同日上午 `A8` 还出现过一次原生
`0xC0000005` 访问违例（`exit=-1073741819`）。结合本机 3 周内 5 次 BSOD
（`0x101 CLOCK_WATCHDOG_TIMEOUT`、`0x4E PFN_LIST_CORRUPT`）以及刚换过的内存条，
**当前最可辩护的解释是瞬时硬件/驱动故障，而不是可复现的逻辑错误**；按此重写融合
分支等于修一个不存在的 bug。

因此 F9 的落地物是防线而非改写：
- `_assert_model_on_device()`：`model.to(device)` 之后立刻体检，任何参数/缓冲区不在
  目标 device 就点名报错（而不是等到 `backward()` 里出现无名 `mat2 is on cpu`）；
- `_assert_batch_on_device()`：每个 train/val step 前检查 batch 里每个张量都已搬到
  device，防止将来 `dataset.py` 新增 key 而 `train.py` 忘记搬运；
- `scripts/verify_device_guards.py`：上述两条的回归测试（含 `cuda` vs `cuda:0`
  比较陷阱——`torch.device("cuda") != torch.device("cuda:0")`，天真写法会把
  正常模型全判成"跑到 CPU 上了"）。

若 阶段 1 冒烟仍复现该错误，说明它不是瞬时故障，届时再按新证据重开。

### 2.3 F8 的连带 bug：bf16 autocast × class weights（已修）

上面这次冒烟第一次跑就崩在损失函数：

```
File "train.py", line 518, in train_epoch
    cls_loss += block_cls_loss(
File "train.py", line 405, in block_cls_loss
    return F.cross_entropy(
RuntimeError: expected scalar type BFloat16 but found Float
```

原因：`block_cls_loss()` 只把 class weights 搬到了 logits 的 **device**，
没对齐 **dtype**。amp 打开时 logits 是 bf16，而权重张量是 fp32，
`cross_entropy` 拒绝这对组合。旧矩阵没暴露它，只是因为旧默认是
**`--class_weight_mode none`（`weight=None`）**；F8 把默认改成 `inverse`
之后这条路才第一次被走到。**如果不做这次冒烟，阶段 1 的 2 小时会直接崩在这。**

修法：`class_weights.to(device=logits.device, dtype=logits.dtype)`（focal 分支
同理对齐到 `focal.dtype`）。修后同一个冒烟配置跑通，见 §2.2。

待定（等 §8 的 D2 决策一起看）：是否把损失整体抬到 fp32 计算而非 bf16。
本机类别权重跨度达 3 个数量级（最大 9.562 / 最小 0.006），fp32 会更稳，
但那属于"换数值口径"，需要在 pilot 阶段用曲线确认，不在本轮顺手改。

### 2.4 "支持度分层"是什么，以及它为什么能解释旧矩阵的反常

**定义**：`macro F1` 把 19 个类**等权**平均，于是一个只有 13 个 val 块的类，
和拥有 35,887 个 val 块的类，对总分的影响力完全一样。支持度分层就是按
**每类在评估集里的块数**把类分成若干档，**在档内分别算 macro F1**，
再连同整体 macro F1 一起报告。

本机 val 的支持度分布（`scripts/paper/support_stratified.py` 输出）：

| 档位 | 类数 | val 块数 | 占 val |
|---|---|---|---|
| `<100` | 2 | 83 | 0.1% |
| `100–999` | 10 | 2,856 | 4.6% |
| `1k–5k` | 4 | 8,629 | 13.9% |
| `5k+` | 3 | 50,514 | **81.4%** |

**为什么必须分层**：`<100` 档只有 2 个类、共 83 个块，单个块就能让某类 F1
跳动约 1/13 ≈ 7.7 个百分点。于是整体 macro F1 的**行间差异**极易被这 0.1%
的数据主导。拿旧矩阵 9 行实测验证（`best-val-acc` 口径，与仪表盘一致）：

```
行间极差(max-min)：整体 macroF1 = 0.0836
                   <100  档     = 0.2534   ← 3 倍于整体
                   100-999 档   = 0.1123
                   1k-5k 档     = 0.0603
                   5k+ 档       = 0.0462   ← 占 81.4% 的数据，反而最稳
```

具体到 `full_3ep`：它的整体 macro F1 是 9 行里**最低**（0.8416），看起来
"完整模型最差"；但拆档后，它在占 81.4% 数据的 `5k+` 档上是 **0.9801（第 2 高）**，
真正的缺口全在 `<100`（0.3198，最低）和 `100-999`（0.8586，最低）两个小档。
而 `full_3ep` 被 `best-val-acc` 选中的是 **ep1——欠训练的轮次**
（train_loss=1.2005，全 3 轮里第 2 高）。

**结论**：旧矩阵"消融打败完整模型"的排序，主要是
(a) macro F1 被 0.1% 的稀有类主导，叠加
(b) `best-val-acc` 选中了欠训练轮次
两件事共同造成的，而不是"主张 3 不成立"。这也正是 D2（口径）必须和 D5
（硬件）分开决策的原因：**口径会翻转排序，必须先定死。**

## 8. 需要你拍板

**D1 热启动怎么处理？（2026-09-25 修订：结论已反转为推荐方案 A）**

- **方案 A（推荐）**：完全去掉 `--init_from`，从预训练 RoBERTa + ViT 起步。
  代价：收敛变慢，epoch 预算可能升到 5–6，合计 ≈135–165 h。
  理由：这是**唯一架构中立**的起点。共享热启动的本质问题是——任何共享起点都携带了
  “产生它的那套架构已经解出这个任务”这一信息（见 §1.1 补查：ft3 是 35 轮完整架构收敛解）。
  消融行从一个已解出任务的解出发、只微调 3 轮，**结构上就不可能暴露“没有这个组件就学不会”**。
  这正是旧表排名翻转的机制。

- **方案 B（原“省 1/3”方案，现已不推荐）**：先训一个“干净 ft0”（只用当前 train split），
  再让各行从 ft0 热启动。**它只解决了泄漏，没有解决上面这个混淆**：
  ft0 仍然是从完整架构训出来的收敛解，各行仍然是在它之上微调。
  换句话说，方案 B 干净了“有没有见过 val/test”，但没干净“起点是否已经解出任务”。
  如果你的目标只是前者的合规性、且接受后者的局限，它仍可用（≈85–115 h），
  但**必须在论文里写成两阶段微调，并对至少一个消融行加“从零 vs 从 ft0”的对照来量化这个混淆**。

- **方案 B′（折中，可选）**：做**领域自适应预训练（DAPT）**——只训编码器、丢弃任务头，
  在 train split 上跑若干 epoch，得到一份**架构中立**的初始化；各消融行从它出发，
  各自训练完整的架构与头部。这样既保留了收敛上的头势，又不携带“某个架构的解”。
  代价：多一次 DAPT 跑（约 5–8 h）。**若 pilot 显示方案 A 收敛太慢，这是首选的补救。**

## 10. 与旧结论的关系
